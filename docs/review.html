Intel Arc iGPU · LLM inference · review

arcinfer

This review covers the OpenCL engine up to 15 October 2026. Since 16 October the default engine is arcinferzero (the same kernels on Level Zero, bit-identical output, MoE experts streamed from the SSD); current speeds: performa-zero-2026-10-16.html.

Ulasan ini membahas engine OpenCL sampai 15 Oktober 2026. Sejak 16 Oktober engine bawaannya arcinferzero (kernel yang sama lewat Level Zero, hasil identik per bit, expert MoE dibaca dari SSD); kecepatan terbaru: performa-zero-2026-10-16.html.

A from-scratch inference engine for Intel's integrated Arc graphics, built on one laptop to shrink the wait before an LLM starts answering a long prompt. It runs Qwen3.5, Qwen3.6 and Qwen3.8 (dense and mixture of experts) and Gemma 4 with image input, serves an OpenAI-compatible API to the Pi coding agent, and is measured here against llama.cpp tuned on both of its Intel backends.

Mesin inferensi yang dibuat dari nol untuk GPU Intel Arc terintegrasi, di satu laptop, untuk memangkas waktu tunggu sebelum LLM mulai menjawab prompt panjang. Ia menjalankan Qwen3.5, Qwen3.6 dan Qwen3.8 (dense dan mixture of experts) serta Gemma 4 dengan input gambar, melayani API kompatibel OpenAI untuk agen pemrograman Pi, dan di sini dibandingkan dengan llama.cpp yang sudah di-tuning pada kedua backend Intel-nya.

  • Arc iGPU · 112 EU · no XMX

Why build another engine

Kenapa membuat engine sendiri

Coding agents such as Pi send the model long prompts: the system prompt, tool definitions and whole source files. On this laptop's integrated GPU, llama.cpp processes a 27B model's prompt at 20 to 40 tokens per second, so an 11,000-token code prompt takes eight to ten minutes before the first word appears. The chip has no matrix engines (XMX); its fastest arithmetic is the int8 dot-product instruction DP4a, which reaches about 13 TOPS in a microbenchmark. arcinfer is organized around that one instruction.

Agen pemrograman seperti Pi mengirim prompt yang panjang ke model: prompt sistem, definisi tool, dan isi file kode. Di GPU terintegrasi laptop ini, llama.cpp memproses prompt model 27B pada 20 sampai 40 token per detik, sehingga prompt kode 11.000 token butuh delapan sampai sepuluh menit sebelum kata pertama muncul. Chip ini tidak punya mesin matriks (XMX); aritmetika tercepatnya adalah instruksi dot-product int8 DP4a, sekitar 13 TOPS dalam microbenchmark. arcinfer dibangun di sekitar satu instruksi itu.

From start to finish

Dari awal sampai akhir

The engine was built in stages, each measured before the next began. The yardstick through most of it was the time to first token of the 27B model on an 11,240-token code prompt.

Engine ini dibangun bertahap, dan setiap tahap diukur sebelum tahap berikutnya dimulai. Tolok ukur utamanya adalah waktu sampai token pertama model 27B pada prompt kode 11.240 token.

    setup.cmd checks the requirements, builds, downloads the chosen models and connects Pi, and can be run again at any time.   16. 16
    Gemma 4 E4B: decoding no longer costs as much as reading
    A profile of one generated token showed E4B's 4-bit (IQ4_XS) matrix-vector products at 44–65 GB/s, and ablations showed why: unpacking the codebook indices cost as much as reading them. A new kernel loads each block straight into registers and packs four weights with four lookups in pre-shifted tables; the FFN's gate, up, GELU and quantization run as one kernel; Q6_K output heads use the same kernel (also for Qwen3.5 4B and Gemma 4 12B). Every step's logits are bitwise identical to before. Long prompts: E4B's head-512 global layers moved to the split-head prompt attention of the 12B.
    E4B generation 17.2 → 21.2 tok/s, with the drafter ~23 → 30.7 · 14K-token prompt 23.5 → 21.8 s
  17. 17
    Images for Qwen3.5, on the GPU
    The Qwen3-VL image encoder runs on the iGPU. With the language model's int8 matrix products it drifted 10–23 % from an f32 reference on photos; emulating each rounding on the CPU showed that the vision transformer, unlike the language model, needs floating point throughout, so it runs f16 weights with f32 activations and attention. A new attention kernel (one query row per lane, keys broadcast) made large images 2.4× faster. The language model got Qwen's M-RoPE positions for image tokens. Pi, the web UI and the API send images to Qwen3.5 4B.
    error 0.2–0.6 % · ~250-token image 0.4 s, 2048 tokens ~5 s, 4096 tokens 15 s (llama.cpp: 71 s) · a 6750-px logo read exactly
  18. 18
    Weights decoded once
    The just-in-time weight decoding reads each superblock with vector loads (it read global memory byte by byte), and the automatic context now keeps a model's decoded weights resident when at least 128K tokens of context still fit, instead of decoding every matrix again on every request. The GEMM itself measured at its practical ceiling: about 65 % of the DP4a peak, loads and per-block scales taking the rest.
    27B decoding per 11K prompt 5.8 → 2.2 s · Qwen3.5 9B, short prompt 1.05 → 0.27 s to the first token

What arcinfer does differently

Apa yang dilakukan arcinfer secara berbeda

  • int8 everywhere it counts. Prompt-processing matrix multiplications run on DP4a with int8 activations (one scale per 32 values) at 8–9 TOPS. Attention is int8 end to end: an int8 K/V cache, DP4a scores, and P·V on DP4a with P quantized per 16-key tile.
  • Weights decoded just in time. Every GGUF quant type (IQ1–IQ4, Q2–Q8 K-quants) is decoded on the GPU into one int8 layout right before its multiplication, so one fast kernel serves all of them and a 27B model only has to fit in its compressed form.
  • Kernels for the model, not for a framework. The DeltaNet recurrence keeps a whole 128-value state column per SIMD lane; the mixture-of-experts kernels multiply straight on 2-bit expert codes; token generation reads the raw quantized blocks at 60–77 GB/s.
  • Speculative decoding without changing the output. Qwen's own MTP head or the Gemma 4 assistant drafter proposes tokens; one main-model pass verifies them and the next token is still sampled from the model.
  • A complete server. OpenAI-compatible API, reasoning and tool calls streamed as they are written, image input, prefix caching for agent loops, conversations and system prompts kept across sessions, restarts and model switches (system prompts per project folder), cancellation within a layer when the client hangs up, a web UI, one command to set everything up (setup.cmd) and one to start Pi (pi-arc), which switches models from inside Pi.
  • int8 di semua bagian penting. Perkalian matriks saat memproses prompt berjalan di DP4a dengan aktivasi int8 (satu skala per 32 nilai) pada 8–9 TOPS. Attention memakai int8 dari awal sampai akhir: cache K/V int8, skor DP4a, dan P·V di DP4a dengan P dikuantisasi per tile 16 key.
  • Bobot di-decode tepat waktu. Semua tipe kuantisasi GGUF (IQ1–IQ4, K-quant Q2–Q8) di-decode di GPU ke satu format int8 tepat sebelum perkaliannya, jadi satu kernel cepat melayani semuanya dan model 27B cukup muat dalam bentuk terkompresinya.
  • Kernel untuk modelnya, bukan untuk framework. Rekurensi DeltaNet menyimpan satu kolom state 128 nilai per lane SIMD; kernel mixture of experts mengalikan langsung kode expert 2-bit; generasi token membaca blok terkuantisasi mentah pada 60–77 GB/s.
  • Speculative decoding tanpa mengubah output. Kepala MTP milik Qwen atau drafter assistant Gemma 4 mengusulkan token; satu langkah model utama memverifikasinya dan token berikutnya tetap disampling dari model.
  • Server lengkap. API kompatibel OpenAI, reasoning dan tool call yang dialirkan selagi ditulis, input gambar, cache prefix untuk loop agen, percakapan dan prompt sistem yang disimpan lintas sesi, restart dan pergantian model (prompt sistem per folder proyek), pembatalan dalam satu layer saat klien memutus koneksi, web UI, satu perintah untuk menyiapkan semuanya (setup.cmd) dan satu untuk menjalankan Pi (pi-arc), yang bisa mengganti model dari dalam Pi.

Waktu sampai token pertama pada prompt kode nyata

Two prompts built from local projects: a scan of the supreme-search codebase and of an internal web app, portal-evaluasi. The same text is 11,240 and 33,937 tokens for the Qwen tokenizer and 13,921 and 35,957 for Gemma's. llama.cpp was measured through llama-server with the same token ids, flash attention on and the best micro-batch size per model and backend. llama.cpp cannot load the 2-bit GSQ Qwen3.6-35B-A3B. Qwen3.6-35B-A3B in 2 bits

Qwen3.6-35B-A3B dalam 2 bit

ISTA-DASLab's GSQ checkpoint stores the 256 routed experts in 2 bits ({−2, −1, 0, 1} times a scale per 128 weights) and everything else in int8; only about 3 B of the 35 B parameters are active per token. llama.cpp cannot load it, so tools/convert_gsq.py converts it once into a GGUF that keeps the exact 2-bit codes, and new kernels multiply directly on them. A speed reference on llama.cpp Vulkan with Unsloth's UD-IQ2_M GGUF of the same model (a different 2–3-bit quantization of similar size) was not run: given how slowly llama.cpp processes long prompts here, it did not seem worth the wait.

Checkpoint GSQ dari ISTA-DASLab menyimpan 256 routed expert dalam 2 bit ({−2, −1, 0, 1} dikali satu skala per 128 bobot) dan sisanya dalam int8; hanya sekitar 3 B dari 35 B parameter yang aktif per token. llama.cpp tidak bisa memuatnya, jadi tools/convert_gsq.py mengonversinya sekali ke GGUF yang menyimpan kode 2-bit apa adanya, dan kernel baru mengalikan langsung pada kode itu. Pembanding kecepatan di llama.cpp Vulkan dengan GGUF UD-IQ2_M dari Unsloth untuk model yang sama (kuantisasi 2–3 bit lain dengan ukuran serupa) tidak dijalankan: melihat lambatnya llama.cpp memproses prompt panjang di sini, hasilnya terasa tidak sepadan dengan lamanya menunggu.

Speculative decoding

Speculative decoding

Qwen drafts with the MTP block inside its own GGUF; Gemma 4 with its separate assistant model, which reads the main model's KV cache instead of keeping one of its own. Both reproduce the plain greedy output token for token (tests/run_tests.ps1). The table gives Gemma 4 generation at short context, plain and with drafting: the 12B after a short story prompt, measured after the decode work of 10 October; the E4B after a 160-token code prompt, measured after the work of 12 October (stage 16; through the server with sampling it drafts at 31 tok/s as well). How much drafting gains depends on the text: code and structured answers accept more drafts than a story. Qwen3.8 27B went from 4.1 to 5.3–5.8 tok/s with its MTP head.

Qwen men-draft dengan blok MTP di dalam GGUF-nya sendiri; Gemma 4 dengan model assistant terpisah, yang membaca cache KV model utama alih-alih menyimpan cache sendiri. Keduanya menghasilkan output greedy yang sama persis, token demi token (tests/run_tests.ps1). Tabel berisi generasi Gemma 4 pada konteks pendek, tanpa dan dengan drafting: 12B setelah prompt cerita pendek, diukur setelah perbaikan decode 10 Oktober; E4B setelah prompt kode 160 token, diukur setelah perbaikan 12 Oktober (tahap 16; lewat server dengan sampling, drafting-nya juga 31 tok/dtk). Besar keuntungan drafting tergantung teksnya: kode dan jawaban terstruktur menerima lebih banyak draft dibanding cerita. Qwen3.8 27B naik dari 4,1 ke 5,3–5,8 tok/dtk dengan kepala MTP-nya.

One task on every model

Satu tugas untuk semua model

The same request went to every model through the server, the way Pi or the web UI would send it: “buat html landing page professional toko coklat enak di pondok gede dalam satu file yang ringkas, interaksi dengan animasi, vanilla css, dan vanilla js dengan struktur mvvm” (a compact one-file professional landing page for a chocolate shop in Pondok Gede, animated interactions, vanilla CSS and JS with an MVVM structure). Each model used its own sampling defaults, no reasoning, at most 6,144 output tokens, and speculative decoding where it has a drafter. The pages are the models' unedited output for a fictional shop; only a label was added on top.

Permintaan yang sama dikirim ke setiap model lewat server, seperti yang dilakukan Pi atau web UI: “buat html landing page professional toko coklat enak di pondok gede dalam satu file yang ringkas, interaksi dengan animasi, vanilla css, dan vanilla js dengan struktur mvvm”. Setiap model memakai sampling bawaannya, tanpa reasoning, output paling banyak 6.144 token, serta speculative decoding bila punya drafter. Halamannya adalah keluaran model apa adanya untuk toko fiktif; hanya sebuah label yang ditambahkan di atasnya.

Accuracy

Akurasi

Speed only matters if the answers stay the same. Each architecture was checked against an independent f32 CPU implementation (tools/ref_forward) and against llama.cpp. The table gives the mean KL divergence of the next-token distributions over every position of a test prompt.

Kecepatan hanya berarti kalau jawabannya tetap sama. Setiap arsitektur diperiksa terhadap implementasi f32 independen di CPU (tools/ref_forward) dan terhadap llama.cpp. Tabel berisi rata-rata KL divergence distribusi token berikutnya di semua posisi prompt uji.

  • Greedy continuations are identical to llama.cpp on the 4B, 9B, Gemma 4 12B and E4B test prompts; tokenizer output is identical to llama-tokenize; chat templates render exactly like the GGUF Jinja templates.
  • The audit that mattered: on Gemma 4 the drift from the reference grew with the context, up to a complete flip of the predicted token at a few positions of a code prompt. Re-running the f32 reference with each piece of arcinfer's int8 rounding simulated in turn pointed at the V cache: Gemma's V rows hold a few large values, and one scale per row left the rest with too few levels. One scale per 64 dims removed the flips and halved the drift. It costs Gemma's attention 1.5–1.8× more time; Qwen keeps per-row scales, which measure as accurate there.
  • Gemma 4 stays further from its reference than Qwen: rounding the activations to int8 alone, in the f32 reference, already gives a KL of 0.009 on Gemma against 0.001 on Qwen3.5-4B.
  • Kelanjutan greedy identik dengan llama.cpp pada prompt uji 4B, 9B, Gemma 4 12B dan E4B; hasil tokenizer identik dengan llama-tokenize; template chat dirender persis seperti template Jinja di GGUF.
  • Audit yang paling penting: pada Gemma 4, penyimpangan dari referensi makin besar seiring konteks, sampai token yang diprediksi berbalik total di beberapa posisi prompt kode. Menjalankan ulang referensi f32 dengan tiap pembulatan int8 arcinfer disimulasikan satu per satu menunjuk ke cache V: baris V Gemma berisi beberapa nilai besar, dan satu skala per baris membuat nilai lainnya kehilangan presisi. Satu skala per 64 dimensi menghilangkan prediksi yang berbalik dan memangkas penyimpangan menjadi separuh. Harganya, attention Gemma 1,5–1,8× lebih lama; Qwen tetap memakai skala per baris, yang terukur akurat di sana.
  • Gemma 4 tetap lebih jauh dari referensinya dibanding Qwen: membulatkan aktivasi ke int8 saja, di referensi f32, sudah memberi KL 0,009 pada Gemma dibanding 0,001 pada Qwen3.5-4B.

Context that fits

Konteks yang muat

How much of the laptop's memory the iGPU may use is a driver setting (Intel Graphics Software): 16.5 GiB during the benchmarks, 18.3 GiB now. In practice: Pi on the 27B model

Dalam praktik: Pi dengan model 27B

With pi-arc the server starts in the background on first use and stays loaded. Pi's /model lists every model in the Hugging Face cache, and the server switches to the chosen one in 5–40 s. Pi's system prompt is now about 4,100 tokens (tool definitions, skills, the project folder and its AGENTS.md), so each project has its own. The server processes it once per project, 40 s on the 27B, and keeps the result in memory and on disk, filed under the project folder (its two latest versions, which other projects do not replace). A new session then reaches its first token in 3.9 s on a running server, 5.3 s after a server restart, and 6.8 s after switching back from another model (once the 37 s load is done). Continuing a session (pi-arc -c) right after closing Pi processes only the new message, because the server still holds that conversation; after other sessions that takes the optional session cache, and the conversation held when the server stops is not saved, so after a restart it is processed again.

In an agent loop each request processes only what is new: 5–7 s before the 27B starts writing, even 27,000 tokens into a session; a large tool result costs its length (a 3,000-line command output: 104 s). Writing is what takes the time: the 27B generates 5–6 tokens per second, so a 770-token reply (reasoning and a tool call) takes about two and a half minutes. Esc stops the GPU within about a second, and the next message reuses the whole conversation (5.0 s instead of 21.5 s for a 2,500-token one).

An end-to-end check on 11 October ran Pi with its normal tools, two extensions and a local MCP server in a scratch git project: reading two files in one reply, a minimal edit, a new file with backslashes, quotes, braces and non-ASCII text, a 3,000-line command output, a failing command, an MCP lookup, a commit and a follow-up question. It produced 27 replies and 21 tool calls, every one with valid arguments, no errors from the server or Pi, and every file on disk as requested. The 35B-A3B model answers the same kind of request several times faster, and Gemma 4 12B can be sent screenshots.

Dengan pi-arc, server menyala di latar belakang saat pertama dipakai lalu tetap dimuat. /model di Pi menampilkan semua model di cache Hugging Face, dan server berganti ke model yang dipilih dalam 5–40 detik. Prompt sistem Pi sekarang sekitar 4.100 token (definisi tool, skill, folder proyek dan AGENTS.md-nya), sehingga setiap proyek punya prompt sendiri. Server memprosesnya sekali per proyek, 40 detik pada 27B, lalu menyimpan hasilnya di memori dan di disk, dikelompokkan per folder proyek (dua versi terakhirnya, yang tidak digantikan oleh proyek lain). Sesi baru kemudian sampai ke token pertama dalam 3,9 detik pada server yang menyala, 5,3 detik setelah server di-restart, dan 6,8 detik setelah kembali dari model lain (setelah pemuatan 37 detik selesai). Melanjutkan sesi (pi-arc -c) tepat setelah Pi ditutup hanya memproses pesan baru, karena server masih memegang percakapan itu; setelah ada sesi lain, hal itu butuh cache sesi (opsional), dan percakapan yang dipegang saat server dimatikan tidak disimpan, sehingga setelah restart percakapan itu diproses ulang.

Dalam loop agen, setiap request hanya memproses bagian yang baru: 5–7 detik sebelum 27B mulai menulis, bahkan setelah 27.000 token dalam satu sesi; hasil tool yang besar memakan waktu sesuai panjangnya (output perintah 3.000 baris: 104 detik). Yang memakan waktu adalah menulis: 27B menghasilkan 5–6 token per detik, jadi balasan 770 token (reasoning dan satu tool call) butuh sekitar dua setengah menit. Esc menghentikan GPU dalam sekitar satu detik, dan pesan berikutnya memakai ulang seluruh percakapan (5,0 detik, bukan 21,5 detik, untuk percakapan 2.500 token).

Pemeriksaan menyeluruh pada 11 Oktober menjalankan Pi dengan tool bawaannya, dua ekstensi dan server MCP lokal di proyek git percobaan: membaca dua file dalam satu balasan, edit kecil, file baru berisi backslash, tanda kutip, kurung kurawal dan teks non-ASCII, output perintah 3.000 baris, perintah yang gagal, pencarian lewat MCP, commit, dan pertanyaan lanjutan. Hasilnya 27 balasan dan 21 tool call, semuanya dengan argumen yang valid, tanpa error dari server maupun Pi, dan setiap file di disk sesuai permintaan. Model 35B-A3B menjawab permintaan sejenis beberapa kali lebih cepat, dan Gemma 4 12B bisa dikirimi tangkapan layar.

Limits

Batasan

  • The original goal, an 11,000-token prompt on the 27B model in under a minute, was not reached: about 90 s on a cool laptop, 97 s mid-benchmark. The matrix multiplications alone take about 70 s at 8–9 TOPS; 60 s would need more than 90 % of the DP4a peak. The 35B-A3B mixture of experts does it in about 14 s.
  • Windows with an Intel Arc (Xe-LPG) iGPU only; Qwen3.5 / 3.6 / 3.8 (dense and MoE) and Gemma 4 (12B, E4B text) only. Image input runs for Qwen3.5 4B (on the GPU) and Gemma 4 12B (on the CPU); not yet for the 9B (its wider encoder), the E4B, or the 27B models (no image projector). Audio input for the 12B is written but not yet tested.
  • llama.cpp SYCL on Gemma 4 12B, Gemma's Vulkan perplexity and the UD-IQ2_M reference for the 35B were not run: llama.cpp's prompt processing on this iGPU is slow enough that those runs alone would have taken hours, and the comparison already showed the picture; those cells read “not run”. The generation figures in the charts were measured before the 10 October decode work, which was measured per kernel and at short context; at short context its gain is within run-to-run noise (±4 %), at long context it saves attention time as shown in stage 11. They also predate the 12 October work (stage 16), which made Gemma 4 E4B ~23 % faster and the Q6_K output heads of Qwen3.5 4B and Gemma 4 12B ~8 % faster.
  • The 35B-A3B GSQ checkpoint ships its MTP block without routed experts, so that model runs without speculative decoding.
  • The laptop throttles under sustained load: back-to-back runs are 5–10 % slower than the first one. Every measurement here was preceded by 30 s of idle GPU, for all engines alike.
  • On the 27B every request takes about 3 s before the first token even when only a handful of tokens are new (15 tokens: 2.8–3.8 s). The cause has not been investigated yet; in an agent loop it is paid on every step.
  • A cancelled Gemma 4 prompt can only be rolled back while its sliding-window rings still hold the positions before the block (blocks up to about 8K tokens). After a longer block the conversation is reset and the next request reloads the system prompt from disk.
  • One conversation is held at a time, in GPU memory. Stopping or restarting the server loses it: system prompts come back from disk, but a long session continued afterwards is processed again (27B: about 100 tokens per second). Saved conversations (the session cache, off by default) are written only when the server moves on to another conversation.
  • Target awal, prompt 11.000 token pada model 27B dalam kurang dari satu menit, tidak tercapai: sekitar 90 detik saat laptop dingin, 97 detik di tengah benchmark. Perkalian matriks saja makan sekitar 70 detik pada 8–9 TOPS; 60 detik butuh lebih dari 90 % puncak DP4a. Mixture of experts 35B-A3B melakukannya dalam sekitar 14 detik.
  • Hanya Windows dengan iGPU Intel Arc (Xe-LPG); hanya Qwen3.5 / 3.6 / 3.8 (dense dan MoE) dan Gemma 4 (12B, teks E4B). Input gambar berjalan untuk Qwen3.5 4B (di GPU) dan Gemma 4 12B (di CPU); belum untuk 9B (encoder-nya lebih lebar), E4B, dan model 27B (tidak punya proyektor gambar). Input audio untuk 12B sudah ditulis tetapi belum diuji.
  • llama.cpp SYCL pada Gemma 4 12B, perplexity Vulkan untuk Gemma, dan pembanding UD-IQ2_M untuk 35B tidak dijalankan: pemrosesan prompt llama.cpp di iGPU ini cukup lambat sehingga run itu saja akan memakan waktu berjam-jam, sementara perbandingan yang ada sudah cukup menunjukkan gambarannya; sel itu bertuliskan “tidak dijalankan”. Angka generasi di grafik diukur sebelum perbaikan decode 10 Oktober, yang diukur per kernel dan pada konteks pendek; pada konteks pendek peningkatannya masih dalam rentang noise antar-run (±4 %), pada konteks panjang ia menghemat waktu attention seperti di tahap 11. Angka itu juga diukur sebelum perbaikan 12 Oktober (tahap 16), yang membuat Gemma 4 E4B ±23 % lebih cepat dan output head Q6_K Qwen3.5 4B serta Gemma 4 12B ±8 % lebih cepat.
  • Checkpoint GSQ 35B-A3B membawa blok MTP tanpa routed expert, jadi model itu berjalan tanpa speculative decoding.
  • Laptop melambat saat beban berkepanjangan: run berturut-turut 5–10 % lebih lambat dari run pertama. Setiap pengukuran di sini didahului 30 detik GPU idle, sama untuk semua engine.
  • Pada 27B, setiap request butuh sekitar 3 detik sebelum token pertama walaupun hanya beberapa token yang baru (15 token: 2,8–3,8 detik). Penyebabnya belum diselidiki; dalam loop agen biaya ini dibayar di setiap langkah.
  • Prompt Gemma 4 yang dibatalkan hanya bisa dikembalikan selama ring sliding-window-nya masih menyimpan posisi sebelum blok tersebut (blok sampai sekitar 8K token). Setelah blok yang lebih panjang, percakapan di-reset dan request berikutnya memuat ulang prompt sistem dari disk.
  • Hanya satu percakapan yang dipegang dalam satu waktu, di memori GPU. Mematikan atau me-restart server menghilangkannya: prompt sistem kembali dari disk, tetapi sesi panjang yang dilanjutkan sesudahnya diproses ulang (27B: sekitar 100 token per detik). Percakapan tersimpan (cache sesi, bawaan mati) hanya ditulis saat server berpindah ke percakapan lain.

What did not work

Yang tidak berhasil

  • A SIMD8 GEMM variant (13.7 TOPS in a microbenchmark) was slower in the real kernel; so were several-tokens-per-sub-group DeltaNet convolutions and local-memory staging of the recurrence.
  • f16 P·V accumulation: no faster and less accurate than int8 P·V. 7-bit P: same speed, 1.8× the error.
  • Keeping Q4_K's block minimums exact in the int8 GEMM runs 3× slower and was not more accurate end to end; the requantized form stays.
  • A third Gemma draft per verification pass: 2.67 instead of 2.25 tokens per pass, but each pass costs more, for +1.5 % overall.
  • Faster IQ4_XS decoding for the E4B: a 256-entry byte-pair table conflicted on local-memory banks (66 → 55 GB/s) and register shuffles with a variable lane index halved the speed; the 16-byte table stays.
  • The new decode-attention kernel on Qwen: up to 2× faster for two-row verification passes, but its rows are no longer bit-identical to single-token decoding, which the MTP test requires; Qwen keeps the previous kernels.
  • Varian GEMM SIMD8 (13,7 TOPS di microbenchmark) lebih lambat di kernel sebenarnya; begitu juga konvolusi DeltaNet beberapa token per sub-group dan staging rekurensi di memori lokal.
  • Akumulasi P·V f16: tidak lebih cepat dan kurang akurat dibanding P·V int8. P 7-bit: kecepatan sama, galat 1,8×.
  • Mempertahankan nilai minimum blok Q4_K secara persis di GEMM int8 berjalan 3× lebih lambat dan tidak lebih akurat secara keseluruhan; bentuk yang dikuantisasi ulang tetap dipakai.
  • Draft ketiga Gemma per langkah verifikasi: 2,67 alih-alih 2,25 token per langkah, tetapi setiap langkah lebih mahal, sehingga hanya +1,5 % secara keseluruhan.
  • Decode IQ4_XS yang lebih cepat untuk E4B: tabel pasangan byte 256 entri bentrok di bank memori lokal (66 → 55 GB/s) dan shuffle register dengan indeks lane variabel memangkas kecepatan jadi separuh; tabel 16 byte tetap dipakai.
  • Kernel attention decode baru untuk Qwen: sampai 2× lebih cepat untuk verifikasi dua baris, tetapi barisnya tidak lagi identik bit demi bit dengan decoding satu token, yang disyaratkan tes MTP; Qwen tetap memakai kernel sebelumnya.

Method

Metode

  1. Models: Qwen3.5-4B and 9B UD-Q4_K_XL (Unsloth); Qwen3.8-27B GSQ-RCO IQ3_S-mtp (ISTA-DASLab, mixed IQ1_M–Q6_K per tensor); Gemma 4 12B QAT Q4_K_M and E4B IQ4_XS (community quantizations) with their mmproj and assistant drafters; Qwen3.6-35B-A3B 2-bit GSQ (ISTA-DASLab).
  2. llama.cpp b11527 official Windows builds. Micro-batch size tuned per model and backend over 512 / 1024 / 2048 with flash attention on; SYCL needs GGML_SYCL_ENABLE_VMM=0 on this driver, and its other options were tested and left at their defaults.
  3. Each test preceded by 30 s of idle GPU; throughput is the best of repeated runs for every engine.
  4. Perplexity: 40 chunks of 512 tokens from 500 KB of llama.cpp documentation, second half of each chunk scored (the llama-perplexity method, including its BOS handling).
  5. Scripts and raw results: bench/run_bench.ps1, bench/results/results.jsonl; accuracy: tools/ref_forward, tests/run_tests.ps1; working notes: docs/review_notes.md.
  6. Decode kernels: bench/attn_dec_bench (attention for 1–4 query rows against an int8 cache, checked against a CPU reference) and bench/gemv_bench (GEMV on real model tensors); decode-path accuracy: run --kl-decode. Changes of 10 and 11 October: CHANGELOG.md.
  7. Pi in practice (11 October, Qwen3.8 27B): scripted pi -p sessions, timed from the server log. Cancellation tests ran in an empty folder with --no-tools; the use-case run in a scratch git project with Pi's tools, two extensions and a local MCP server. Exact rollback: the greedy output after a cancelled prompt equals that of a run that never cancelled (27B and Gemma 4 12B). The per-folder system-prompt cache was checked on a separate 4B server with its own cache folder (grouping, two versions per folder, loading after a restart, older files adopted, the size limit) and with one real Pi request.
  8. E4B generation (12 October): run --prof-gen per kernel, bench/gemv_bench per matrix with the weights streaming over all layers (ablations and a bitwise comparison with the old kernel), run --dump-logits for bitwise identity of 64 generation steps, 128 tokens after bench/prompts/gemma-code160, old and new path in the same session. Long prompts: bench/attn_bench at 13,921 tokens, then the 13,921-token code prompt end to end and perplexity over 6 chunks of 4,096 tokens.
  1. Model: Qwen3.5-4B dan 9B UD-Q4_K_XL (Unsloth); Qwen3.8-27B GSQ-RCO IQ3_S-mtp (ISTA-DASLab, campuran IQ1_M–Q6_K per tensor); Gemma 4 12B QAT Q4_K_M dan E4B IQ4_XS (kuantisasi komunitas) beserta mmproj dan drafter assistant-nya; Qwen3.6-35B-A3B GSQ 2-bit (ISTA-DASLab).
  2. llama.cpp b11527 build resmi Windows. Ukuran micro-batch di-tuning per model dan backend dari 512 / 1024 / 2048 dengan flash attention aktif; SYCL butuh GGML_SYCL_ENABLE_VMM=0 di driver ini, dan opsi lainnya sudah diuji lalu dibiarkan default.
  3. Setiap tes didahului 30 detik GPU idle; throughput adalah hasil terbaik dari beberapa run untuk setiap engine.
  4. Perplexity: 40 potongan 512 token dari 500 KB dokumentasi llama.cpp, separuh kedua tiap potongan dinilai (metode llama-perplexity, termasuk penanganan BOS-nya).
  5. Skrip dan hasil mentah: bench/run_bench.ps1, bench/results/results.jsonl; akurasi: tools/ref_forward, tests/run_tests.ps1; catatan kerja: docs/review_notes.md.
  6. Kernel decode: bench/attn_dec_bench (attention untuk 1–4 baris query terhadap cache int8, dicek terhadap referensi CPU) dan bench/gemv_bench (GEMV pada tensor model asli); akurasi jalur decode: run --kl-decode. Perubahan 10 dan 11 Oktober: CHANGELOG.md.
  7. Pi dalam praktik (11 Oktober, Qwen3.8 27B): sesi pi -p yang dijalankan skrip, waktunya diambil dari log server. Tes pembatalan berjalan di folder kosong dengan --no-tools; uji kasus pemakaian di proyek git percobaan dengan tool Pi, dua ekstensi dan server MCP lokal. Pengembalian yang persis: output greedy setelah prompt yang dibatalkan sama dengan run yang tidak pernah dibatalkan (27B dan Gemma 4 12B). Cache prompt sistem per folder diperiksa pada server 4B terpisah dengan folder cache sendiri (pengelompokan, dua versi per folder, pemuatan setelah restart, file lama diambil alih, batas ukuran) dan dengan satu request Pi sungguhan.
  8. Generasi E4B (12 Oktober): run --prof-gen per kernel, bench/gemv_bench per matriks dengan bobot dibaca dari memori untuk semua layer (ablasi dan perbandingan bit demi bit dengan kernel lama), run --dump-logits untuk memastikan 64 langkah generasi identik bit demi bit, 128 token setelah bench/prompts/gemma-code160, jalur lama dan baru dalam sesi yang sama. Prompt panjang: bench/attn_bench pada 13.921 token, lalu prompt kode 13.921 token dari awal sampai akhir dan perplexity atas 6 potongan 4.096 token.
